# v1.5 — Safety, guardrails & evaluation

**Goal:** close the two halves left open. **Safety**: a callable moderation port
and composable guardrails — distinct from the reactive `ContentFilterError`
taxonomy, which only fires *after* a provider refuses. **Monitoring, completed**:
v1.0 gave `Tracer` (telemetry *emission*); this adds the feedback loop —
evaluation (LLM-as-judge) and annotation capture — that turns monitoring from
"observe" into "improve."

**Provider added:** none new — moderation/eval reuse existing chat + a
classification endpoint (e.g. OpenAI moderation, Llama Guard).

**Done when:** a caller can pre-screen content through a neutral moderation port,
wrap any `ChatModel` in guardrail middleware (PII redaction / output validation),
score outputs with an evaluator, and attach feedback that lands alongside trace
spans.

**Not in scope:** building an evals *platform* / dashboard; policy authoring
tooling. ocai provides the neutral ports; the harness around them is the user's.

**Parallelism:** all four WUs are largely independent. 10.2 (guardrails) composes
naturally with 10.1 (moderation) but doesn't require it.

> Read the root [CLAUDE.md](https://github.com/ocarinow/ocai/blob/main/CLAUDE.md) first. `Moderation` and `Evaluator` are
> new additive ports; guardrails and feedback are middleware in the existing
> composable pipeline (rule, the middleware idea) — no breaking change.

---

## WU 10.1 — `Moderation` port  ·  depends on: v1.0

- [ ] Neutral port `Moderation` (`classify(content) -> categories + scores`)
      accepting text and v1.3 content parts. One adapter (a classification
      endpoint), recorded fixtures, golden conformance, cost wired.
- [ ] Clarify the boundary vs `ContentFilterError`: moderation is a *proactive
      call*; the taxonomy error is a *reactive provider signal*. Document both.

**Done:** content classifies into neutral safety categories with scores against
recorded fixtures; the moderation-vs-taxonomy distinction is written down.

---

## WU 10.2 — Guardrails middleware  ·  depends on: v0.2 middleware

- [ ] `ChatModel`-wrapping middleware for input/output guardrails: PII redaction,
      output schema/JSON validation, and optional moderation gating (composes with
      10.1). Each guardrail action is **recorded in the `Report`** — a redaction is
      loss, and loss is data (rule 4).

**Done:** a wrapped model redacts PII and validates structured output, and the
`Report` shows exactly what was redacted/rejected; the middleware composes with
retry/cache/fallback in any order.

---

## WU 10.3 — `Evaluator` port (LLM-as-judge)  ·  depends on: v1.0

- [ ] Neutral port for scoring a response against a rubric/reference
      (`evaluate(input, output, rubric) -> score + rationale`), implemented over
      the existing chat surface. Recorded fixtures; cost wired.

**Done:** an output scores against a rubric through the neutral port with a
rationale, against recorded fixtures, cost reported.

---

## WU 10.4 — Feedback / annotation capture  ·  depends on: 5.2 (`Tracer`)

- [ ] A neutral way to attach feedback (rating, label, free-text) to a request,
      correlated with its trace span so monitoring closes the loop. Pluggable
      sink, same explicit-credential / redaction rules as everything else.

**Done:** feedback attaches to a completed request, correlates with its `Tracer`
span, and flushes to a sink in a test without live services.

---

## After v1.5 — what's deliberately still out

OCR-as-a-distinct-port, fine-tuning/model-management, and adding a **fourth chat
provider** remain out until there is a concrete pull. The roadmap's spine never
changed: prove honest, version-resilient conversion deep before adding breadth —
breadth here was earned by keeping every addition **additive** and every new port
held to the same fidelity-report and recorded-fixture bar as the original three.
